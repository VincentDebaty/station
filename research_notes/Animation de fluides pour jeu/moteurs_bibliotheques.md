# Moteurs et bibliothèques pour un liquide 2D (Godot 4, Unity, web) — inventaire pour un puzzle iPhone

Recherche faite le 14 octobre 2026. Les dates de dernier commit et les étoiles ont été lues directement par l'API GitHub (`gh api repos/...`) ce jour-là ; elles sont citées avec le lien du dépôt.

## Godot 4 : quels greffons de liquide existent, à quel niveau de maturité, et comment écrire le sien ?

### Takeaway
Un seul greffon sérieux et vivant offre un vrai liquide à particules dans Godot 4 : **Godot Rapier Physics** (MIT, GDExtension en Rust, fluides via Salva, nœud `Fluid2D`, rendu par MultiMesh + shader métaballe fourni, version v0.36.0 du 2 octobre 2026, ~1 000 étoiles). Le reste est soit mort (godot-box2d archivé en 2024, LiquidFun absent), soit d'une autre nature (automates cellulaires, Euler sur grille, FLIP en compute shader GPL). Écrire sa propre simulation reste viable : GDScript typé suffit pour quelques centaines de particules, mais au-delà il faut du C++/Rust en GDExtension, C# sur iOS étant encore « expérimental ».

### Cited Findings
**Godot Rapier Physics (appsinacup)**
- Dépôt `appsinacup/godot-rapier-physics` : 1 024 étoiles, dernier push le 12 oct. 2026, licence MIT ; description : « 2D and 3D physics engine… with better stability, performance, liquids, determinism, state serialization and no ghost collisions » — [GitHub](https://github.com/appsinacup/godot-rapier-physics)
- Dernières versions : v0.36.0 (2 oct. 2026), v0.35.4 (8 sept. 2026), v0.35.3 (30 août 2026), v0.35.2 (10 août 2026) : cadence de sortie mensuelle ou plus — [Releases GitHub](https://github.com/appsinacup/godot-rapier-physics/releases)
- README : « Works on: Desktop, Mobile and Web » ; builds pour Godot 4.4 à 4.7 (features `api-4-4` … `api-4-7`) ; fluides simulés par la bibliothèque Salva ; sauvegarde/chargement de l'état physique (serde) — [GitHub README](https://github.com/appsinacup/godot-rapier-physics)
- Le site du greffon le décrit comme simulant « des fluides de densité et viscosité différentes qui interagissent avec les autres objets » — [godot.rapier.rs](https://godot.rapier.rs/)
- Tutoriel officiel « Create a fluid » : nœud **`Fluid2D`**, propriété `Points` (les particules), scripts d'exemple `fluid_2d_circle.gd` / `fluid_2d_rectangle.gd` pour remplir une forme, `Density` (1000 dans l'exemple, ce qui rend le fluide lourd — les RigidBody doivent avoir plus de masse), tableau d'`Effects` combinables : `FluidEffect2DSurfaceTensionAKINCI` (coef. 100 « pour un comportement d'eau »), `FluidEffect2DElasticity`, `FluidEffect2DViscosityArtificial` ; avertissement : des valeurs trop hautes ou trop basses font exploser la simulation — [Tutoriel godot.rapier.rs](https://godot.rapier.rs/docs/tutorial/create-a-fluid)
- Rendu fourni : `MultiMeshInstance2D` + `fluid_2d_renderer.gd` (une sprite par particule), ou `fluid_2d_shader_renderer.gd` dans un `CanvasLayer` séparé : le shader floute les disques, coupe l'alpha à 0,8 et recolore → surface « métaballe » continue — [Tutoriel](https://godot.rapier.rs/docs/tutorial/create-a-fluid)
- Rayon de particule global : Project Settings > Physics > Rapier > Fluid, défaut 20 ; « un rayon plus petit demande plus de particules, ce qui peut donner de mauvaises performances sur de grands volumes d'eau » — [Tutoriel](https://godot.rapier.rs/docs/tutorial/create-a-fluid)
- Le tutoriel ne documente pas d'API d'ajout/suppression de particules à l'exécution (il renvoie à une page de référence « Fluid Nodes ») ; la PR #440 (nov. 2025) a ajouté `get_particle_in_circle/sphere` — [Tutoriel](https://godot.rapier.rs/docs/tutorial/create-a-fluid) ; [Issue #440](https://github.com/appsinacup/godot-rapier-physics/issues/440)
- Bugs ouverts sur les fluides : #551 (juin 2026) `FluidEffect2DViscosityDFSPH` fait paniquer le solveur Salva (`assertion failed: !denominator.is_zero()`) quel que soit le coefficient ; le mainteneur renvoie la correction à Salva ; #300 (rendu 3D des fluides) ouvert depuis 2024. Corrigés récemment : #636 « fluid2d: fix canvas layer cutting off » (sept. 2026), #456 « Fluid2d effects dont apply on the fluids » (nov. 2025), test 2D fluides ajouté en sept. 2026 (#631, #639) — [Issue #551](https://github.com/appsinacup/godot-rapier-physics/issues/551) ; [recherche d'issues](https://github.com/appsinacup/godot-rapier-physics/issues?q=fluid)
- iOS : issue #572 (juin 2026) « Unable to build on Xcode » avec Godot 4.7 + Rapier2D 0.8.37 — fermée, l'auteur reconnaît que l'erreur venait d'une autre extension ; il précise que l'archive Xcode fonctionnait avec Godot 4.6.3 — [Issue #572](https://github.com/appsinacup/godot-rapier-physics/issues/572)

**Salva (moteur de fluide sous Godot Rapier)**
- `dimforge/salva` : 703 étoiles, licence Apache-2.0, dernier commit 8 août 2026 (« Release v0.10.0 », mise à jour vers rapier 0.35) ; avant cela juin 2026 puis février 2025 — activité faible mais réelle — [GitHub](https://github.com/dimforge/salva)

**Rendu et calcul GPU sous Godot iOS**
- Les compute shaders passent par `RenderingDevice`, qu'utilisent Forward+ et Mobile (Vulkan, D3D12 ou Metal) mais **pas** le moteur Compatibilité (OpenGL) ; si RenderingDevice n'est pas supporté, Godot 4.4+ retombe sur Compatibilité — [Docs Godot, renderers](https://docs.godotengine.org/ru/4.4/tutorials/rendering/renderers.html) ; [Architecture de rendu](https://docs.godotengine.org/zh-cn/4.x/engine_details/architecture/internal_rendering_architecture.html)
- Pilote Metal natif depuis Godot 4.4 (expérimental à l'époque), utilisable par Forward+ et Mobile ; shaders transpilés GLSL→MSL via SPIRV-Cross — [Architecture de rendu](https://docs.godotengine.org/zh-cn/4.4/contributing/development/core_and_modules/internal_rendering_architecture.html)
- Témoignage (forum Apple) : compilation des shaders en MSL au premier lancement, gel de plus de 5 s la première fois, ~1,5 s ensuite — anecdotique — [Apple Developer Forums](https://developer.apple.com/forums/thread/824902)

**Écrire sa propre simulation : GDScript, C#, GDExtension**
- FAQ Godot : C# est plus rapide que GDScript quand il appelle peu le moteur, peut être plus lent quand il fait beaucoup d'appels d'API (marshalling), le GC peut provoquer des à-coups ; « C++, using GDExtension, will almost always be faster than either » — [FAQ Godot](https://docs.godotengine.org/it/4.5/_sources/about/faq.rst.txt)
- Un fil du forum Godot rapporte un même calcul optimisé de 7 208 ms à 147 ms en GDScript et de 66 ms à 3 ms en C++ (≈50× d'écart après optimisation des deux) — configuration non vérifiable — [Forum Godot](https://forum.godotengine.org/t/is-the-speed-of-c-and-gdscript-equal/99307)
- C# vers iOS : documentation 4.5 « iOS support is currently experimental » (NativeAOT .NET 8, seul runtime possible, export depuis un Mac) ; un membre de l'équipe sur le forum (non officiel) évoque un retrait de l'avertissement « en 4.6 ou 4.7 » faute de rapports critiques ; le trimming n'est pas pleinement compatible avec les bindings — [Docs C# 4.5](https://docs.godotengine.org/en/4.5/tutorials/scripting/c_sharp/index.html) ; [Forum Godot](https://forum.godotengine.org/t/is-the-ios-support-good-enough-when-using-the-mono-version-for-a-full-release/128950) ; [PR #82729](https://github.com/godotengine/godot/pull/82729)

### Inferences
- Pour « une boule qui flotte dans un labyrinthe rempli par un robinet et vidé par des bondes », Godot Rapier coche le plus de cases sans écrire de solveur : particules, flottabilité par couplage bidirectionnel, rendu métaballe fourni, état sérialisable. Le risque principal est la **stabilité des paramètres** (explosions signalées par le tutoriel et l'issue #551) et le **coût par particule** sur iPhone, non mesuré publiquement.
- Le robinet (ajout de particules) et les bondes (suppression) dépendent d'une API d'exécution que le tutoriel ne montre pas : à vérifier dans la référence de classe avant de s'engager.
- Si l'on écrit sa propre simulation, GDScript ne convient qu'à un modèle grossier (quelques centaines de particules, ou une grille de hauteurs) ; un vrai SPH/PBF de quelques milliers de particules relève de GDExtension (C++ ou Rust via godot-rust). Le C# sur iOS ajoute un risque de chaîne d'export.
- Un solveur GPU (compute shader) impose le moteur Mobile/Metal et exclut Compatibilité ; il complique aussi le banc headless (voir la section déterminisme).

### Gaps
- Aucun chiffre public de performance de `Fluid2D` (Rapier/Salva) sur iPhone : nombre de particules tenable à 60 i/s inconnu.
- Je n'ai pas trouvé la page de référence des méthodes de `Fluid2D` (ajout/suppression de points à l'exécution) : l'URL `/docs/documentation/liquids` renvoie 404.
- Pas de mesure publique GDScript vs C# vs GDExtension sur un SPH 2D, ni sur iPhone.

## Unity : Zibra, Obi, portages LiquidFun, SPH en DOTS/Burst, assets 2D

### Takeaway
Côté Unity, **Obi Fluid** est la seule solution commerciale de particules activement maintenue avec un **mode 2D explicite** (≈55-60 $, v7.2 du 26 août 2026, backends Burst CPU ou Compute GPU). **Zibra Liquid** est un liquide 3D GPU, compatible iOS (Metal, iPhone 6s+), mais sans mise à jour depuis mai 2024. Les assets « 2D water » bon marché sont vieux ou abandonnés, LiquidFun n'a pas de portage Unity maintenu, et les références SPH (Sebastian Lague, ECS SPH) sont des démos, pas des bibliothèques.

### Cited Findings
- **Obi Fluid** : 55,20 € HT (60 $ selon une autre source), version 7.2 du 26 août 2026, Unity d'origine 6000.0.82, 100 avis, licence « Extension Asset » (EULA standard) ; la page ne liste pas les plateformes — [Unity Asset Store](https://assetstore.unity.com/packages/tools/physics/obi-fluid-63067) ; version 7.1.1 du 22 avril 2026 citée par [une recherche](https://assetstore.unity.com/packages/tools/physics/obi-fluid-63067/reviews)
- Obi : « The solver can simulate in 2D or 3D mode. In 2D mode, simulation only happens in the XY plane », compatible collisionneurs 2D ; modes synchrone / asynchrone (rendu en retard d'une image) / synchrone fixe — [Manuel Obi, ObiSolver](https://obi.virtualmethodstudio.com/manual/7.0/obisolver.html)
- Obi backends : Burst (CPU, multithread + SIMD, défaut depuis Obi 5.6, « performs best for small simulations », tourne partout où Burst compile) ou Compute (GPU, « as long as your device supports compute shaders », meilleur pour les très grandes simulations, coût minimal plus élevé) — [Manuel Obi, backends](https://obi.virtualmethodstudio.com/manual/7.0/backends.html)

### Inferences
- Pour un solo qui veut un liquide 2D « qui a l'air vrai » sans écrire de solveur, Obi Fluid en mode 2D + backend Burst est la seule option commerciale actuelle et crédible ; Zibra est surdimensionné (3D, GPU haut de gamme) et semble ralenti depuis 2024.
- Le surcoût Unity (moteur, compte, licence) pèse plus que le prix de l'asset pour un projet qui vise par ailleurs Godot.
- Aucune des solutions Unity n'annonce de déterminisme multiplateforme ; Obi avec backend Compute GPU est a priori non déterministe entre appareils.

### Gaps
- Pas de benchmark Obi Fluid 2D sur iPhone récent ; un chiffre « iPhone 4S, 600 particules à ~50 i/s » circule sur un agrégateur sans provenance fiable, je ne le retiens pas.
- Le manuel Obi ne dit rien du déterminisme.
- Pas trouvé de portage LiquidFun pour Unity maintenu ; Fluvio n'a pas été retrouvé dans les résultats (probablement abandonné, non confirmé).

## Web (JS/TS) : LiquidFun/box2d-wasm, Rapier, Salva, métaballes, démos SPH/PBF/FLIP, Safari iOS

### Takeaway
Le web n'a **aucune bibliothèque de liquide à particules à la fois maintenue et éprouvée** : les builds LiquidFun en WASM datent de 2022 au mieux, Rapier.js n'expose **pas** les fluides de Salva, et le seul projet actif (un portage LiquidFun sur Box2D 3.2 en WASM, sept. 2026) est un dépôt solo à 0 étoile. En revanche, les **démos de référence** (Ten Minute Physics FLIP, Sebastian Lague) et la technique de rendu métaballe (flou + seuil) sont simples à reprendre à la main, et WebGPU est actif par défaut dans Safari 26 sur iOS 26.

### Cited Findings
- `liquidfun-wasm` (npm) : v7.0.0, dernière modification 8 mai 2022, Zlib, compatible Box2D 2.4.1 ; `box2d-wasm` : v7.0.0, modifié avril 2022 — lus par `npm view` ; [npm liquidfun-wasm](https://www.npmjs.com/package/liquidfun-wasm)

### Inferences
- Pour un prototype web, l'option la plus sûre n'est pas une bibliothèque mais un **solveur maison court** (PBF/SPH à hachage spatial, ou FLIP à la Ten Minute Physics) en JS pur, rendu par flou + seuil sur canvas/WebGL. C'est aussi la voie la plus portable vers Godot (le même algorithme se réécrit en GDScript/C++).
- Le dépôt de prototype actuel de Station (« Labyrinthe d'eau », commits récents : « l'eau se calcule en petites cases, quatre fois plus fine », « une nappe au contour lissé ») est déjà sur cette voie maison, par grille.
- `liquidfun-wasm` peut servir à un essai rapide, mais il est figé depuis 2022 et repose sur un code abandonné ; à éviter pour quoi que ce soit de durable.
- WebGPU sur iOS 26 rend possible un solveur GPU dans Safari, mais cela exclut les iPhone non mis à jour et casse l'équivalence avec un banc Node CPU.

### Gaps
- Pas de mesure publique de PBF/SPH/FLIP JS dans Safari iOS (nombre de particules à 60 i/s).
- Je n'ai pas vérifié si `liquidfun-wasm` expose réellement `b2ParticleSystem`.
- La licence de `matthias-research/pages` n'est pas déclarée : réutiliser son code tel quel est juridiquement flou (s'en inspirer reste possible).

## Déterminisme et banc d'essai headless (rejouer des séquences d'appuis pour prouver qu'un niveau est soluble)

### Takeaway
**Rapier** est la seule pile du lot qui revendique un déterminisme **multiplateforme** — en JS (`@dimforge/rapier2d-deterministic`) et dans Godot Rapier (build « enhanced-determinism ») — mais l'historique montre que cette promesse a été cassée et réparée en juin 2026, et elle ne couvre pas explicitement les fluides Salva. Pour un puzzle, le plus robuste est de ne pas dépendre du déterminisme multiplateforme : faire tourner le banc et le jeu sur **le même code**, à pas fixe, et vérifier la solubilité avec une marge de tolérance. Godot (`--headless --script --fixed-fps`) et Node savent tous deux faire tourner ce banc.

### Cited Findings
- Rapier JS : la doc déclare la version WASM « fully cross-platform deterministic » à condition d'avoir la même version, les mêmes conditions initiales, les corps ajoutés/retirés dans le même ordre, et des valeurs d'initialisation elles-mêmes déterministes (`Math.sin`/`Math.cos` peuvent différer selon les plateformes) ; vérification par `world.takeSnapshot()` + hash MD5 — [Rapier, Determinism (JS)](https://rapier.rs/docs/user_guides/javascript/determinism)
- **Contradiction** : le README npm de Rapier 2D dit que le paquet standard « does **not** guarantee cross-platform determinism… (but it is still locally deterministic) » et que `@dimforge/rapier2d-deterministic` est « A less optimized build but with a guarantee of a cross-platform deterministic execution » ; ce paquet existe en v0.21.0 — [npm @dimforge/rapier2d-deterministic](https://www.npmjs.com/package/@dimforge/rapier2d-deterministic)
- Godot Rapier : README actuel « Exact simulation every time (on same platform) » et « Exact simulation on multiple platforms », `enhanced-determinism` activé dans toutes les builds — [GitHub README](https://github.com/appsinacup/godot-rapier-physics) ; l'Asset Library listait une variante « Slower Version with Cross Platform Deterministic » (sans SIMD ni solveur parallèle, « not for normal use cases ») — [Asset Library](https://godotengine.org/asset-library/asset/edit/13177)
- Historique : issue #558 (juin 2026) — la build `godot-rapier-2d-single-enhanced-determinism` v0.8.34 donnait des états différents entre Mac M1 (ARM) et Windows x86_64 ; corrigée par la PR #559 (« non cross platform deterministic math was applied in various places. I've fixed those I've seen, hoping I did not missed any ») et des tests de déterminisme multiplateforme (#561) ; #564 : enhanced-determinism ne garantissait pas le déterminisme 3D — [Issue #558](https://github.com/appsinacup/godot-rapier-physics/issues/558) ; [PR #559](https://github.com/appsinacup/godot-rapier-physics/pull/559) ; [Issue #564](https://github.com/appsinacup/godot-rapier-physics/issues/564)
- Issue #226 ouverte depuis août 2024 : exposer des types et fonctions de mathématiques déterministes côté script — [Issue #226](https://github.com/appsinacup/godot-rapier-physics/issues/226) ; issue #534 ouverte : désynchronisations en résimulation (rollback réseau) — [Issue #534](https://github.com/appsinacup/godot-rapier-physics/issues/534)
- Godot en ligne de commande (doc 4.7) : `--headless` (« --display-driver headless --audio-driver Dummy », « useful… with --script ») ; `-s/--script` ; `--fixed-fps <fps>` (« disables real-time synchronization ») ; `--disable-render-loop` ; `--quit-after <n>` ; `--time-scale` ; `--main-loop` ; `--write-movie` (force `--fixed-fps`) ; les arguments inconnus sont ignorés **sans avertissement** — [Docs Godot, command line](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)
- Box2D/LiquidFun et le portage Box2D 3.2 + LiquidFun en WASM compilent avec `-ffast-math`, ce qui autorise le compilateur à réordonner les calculs flottants — [GitHub brotochola](https://github.com/brotochola/Box2d_3.2_C_-_liquidfun)

### Inferences
- Les fluides de Godot Rapier passent par Salva ; ni le README ni les tests cités ne disent que les particules Salva sont couvertes par la garantie multiplateforme (les tests mentionnés portent sur les corps rigides et l'état physique). À traiter comme **non garanti** tant qu'un test ne le prouve pas.
- Toute solution GPU (compute shader Godot, WebGPU, Obi Compute, Zibra) est à exclure si le banc doit reproduire exactement le jeu : l'ordre des opérations flottantes sur GPU dépend du pilote.
- Schéma de banc réaliste : (a) web — le moteur de simulation dans un module JS pur, sans DOM, chargé tel quel par Node (comme `tools/ecluses-banc.mjs` et `tools/fete-banc.mjs` le font déjà en extrayant le moteur de la page) ; (b) Godot — un script lancé par `godot --headless --script banc.gd` (ou une scène avec `--fixed-fps 60 --quit-after N`) qui rejoue des séquences « robinet ouvert de t1 à t2, bonde k ouverte à t3 » et vérifie que la boule atteint la sortie. Un solveur maison en double précision et à pas fixe, sans fonctions transcendantes dans la boucle, est déterministe sur une même plateforme ; le banc garde alors son autorité tant que le jeu et le banc partagent le même binaire/code.
- Pour un puzzle, mieux vaut des critères de victoire tolérants (niveau d'eau au-dessus d'un seuil, boule dans une zone) que des positions exactes : cela rend la solubilité robuste aux petites divergences entre appareils.

### Gaps
- Aucune source ne confirme que les fluides Salva sont déterministes entre ARM (iPhone) et x86/ARM Mac.
- Aucune documentation trouvée sur un banc headless spécifique aux fluides Godot Rapier (le mainteneur a des tests CI, mais leur contenu fluide n'a pas été lu au-delà des titres #631/#639).
- Pas de bibliothèque à virgule fixe pour fluides 2D identifiée (non recherchée en profondeur faute d'appels restants).
